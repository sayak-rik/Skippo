Version: 2.2
Date: April 17, 2026
Prepared For: Skippo product planning and engineering execution

1. Executive Summary

Skippo is no longer just a school transport safety platform. It should be positioned as a unified school operations platform that connects transport, classroom visibility, compliance, communications, and parent engagement.

The platform will support five primary surfaces:

  • Parent App: live transport tracking, alerts, student progress, attendance visibility, and message center.
  • Driver App: trip lifecycle, assigned vehicle, SOS, OTP login, and document renewal workflows.
  • Teacher App: classroom attendance, student progress updates, and parent-visible academic signals.
  • School Dashboard: highly flexible control center for transport, academics, staff, messaging, compliance, and reporting.
  • Backend Platform: APIs, auth, data models, real-time systems, notifications, analytics, and integrations.
Core product thesis: Schools need operational control, parents need trust and visibility, and staff need fast, low-friction tools. Skippo should become the operational layer connecting those needs.

2. Product Vision

Skippo should help schools answer five questions in real time:

  • Where is the student during the transport journey?
  • Was the student present in school and in class today?
  • Is the assigned driver, bus, and compliance documentation valid?
  • How can the school communicate updates and notices to parents reliably?
  • What operational risks require intervention right now?

4. Product Surfaces and Feature Scope

4.1 Parent App

  • OTP login and student-linked account access
  • Live trip map with real-time vehicle position
  • Boarded, dropped, delayed, route deviation, and SOS alerts
  • Daily school attendance visibility from teacher input
  • Student progress feed showing notes, milestones, and school updates
  • Message center for notices, announcements, campaigns, and ads
  • Past alerts and trip history
  • Driver and vehicle profile view where appropriate

4.2 Driver App

  • OTP login with support for two active devices per driver
  • Assigned vehicle and route view
  • Trip start and end controls
  • Live background GPS tracking
  • Boarded and dropped actions for students
  • SOS trigger with escalation to school, parents, and configured emergency contacts
  • NOC, insurance, permit, pollution, and fitness document expiry reminders
  • Upload and review compliance documents

4.3 Teacher App

  • Invite-link signup — admin dashboard sends an email invite; teacher registers and goes through first-week class-selection onboarding
  • OTP or school-issued login for returning teachers
  • Classroom and section assignment; teacher sees today's schedule with the current class pinned to top
  • Daily attendance marking per student — mark present or absent, both synced to backend and visible on the school dashboard
  • Per-student progress notes — category chips (Academic, Participation, Behavior, Homework, Milestone, Concern) plus free-text note; parent-visible immediately
  • Class-wide broadcast — teacher sends a message to all parents of students in the session's classroom in one tap; appears in parent message center
  • Assist requests (doubt cards) — parents raise a question from the parent app; teacher sees a badge on the student card, can read the question and reply with an optional message that goes back to the parent
  • Manual class override — if verbally assigned to a different class, teacher taps "Pick a class" and selects any classroom; the student list auto-loads for that classroom
  • First-week schedule memory — during the first week the teacher manually selects which classes they teach; system saves this as a JSON schedule_preferences field and auto-fills the schedule from week two onwards
  • Absence and issue tagging for escalation

4.4 School Dashboard

  • Live fleet map and trip command center
  • Student, parent, teacher, driver, and vehicle management
  • Route and stop builder
  • Class attendance overview and student performance snapshots
  • Message campaigns and audience targeting
  • Compliance center for document renewals and status tracking
  • Operational reports, exports, and alerts center
  • Customizable dashboard widgets and school-level settings
  • Dedicated school-specific dashboard URL such as a subdomain or mapped custom domain

6. Functional Requirements by Domain

6.1 Authentication and Sessions

  • OTP-based login for parents and drivers
  • School-managed login or OTP login for teachers
  • JWT-based API auth with refresh tokens
  • Device registration and device metadata tracking
  • Driver accounts may remain active on a maximum of two devices at a time
  • Session revocation from dashboard when needed

6.2 Transport Operations

  • Each driver is assigned exactly one active vehicle at a time
  • Each trip is linked to a route, driver, vehicle, school, and roster of students
  • Location updates broadcast every 10 seconds or every 20 meters
  • Trip events should be stored as an auditable timeline
  • Parents only see the trip relevant to their linked student

6.3 Academic Attendance and Progress

  • Teachers can mark daily attendance by class and section — present or absent, both recorded to backend
  • Teachers can add short progress records per student with category and free text; visible to parents immediately
  • Teachers can send a class-wide broadcast message; all parents in the classroom receive a push notification and a message center entry
  • Parents can raise assist requests (doubt cards) from the parent app; teachers see these per-student and can resolve with an optional reply
  • Parents can view student attendance and progress history
  • Dashboard can filter academic data by date, class, teacher, and student
  • Teachers invited via admin-generated link complete signup and first-week class selection; the system persists their classroom choices as a JSON schedule_preferences field on TeacherProfile and generates recurring ClassSession records from week two onwards

6.4 Messaging and Ads

  • Message center stores all notices, updates, alerts, and ad-style campaigns
  • Messages can be targeted by school, class, route, or parent segment
  • Each message tracks publish time, delivery status, and read status
  • Ads should be clearly classified and controlled through dashboard permissions

6.5 Emergency Workflows

  • Driver SOS should instantly notify school admins and parents on the active route
  • The system should support configurable emergency escalation contacts per school or city
  • Civic-body automation should be designed as a configurable workflow and not hardcoded until verified integrations are available
  • Every SOS event should generate an audit trail

6.6 Compliance and Renewal

  • Store document types such as insurance, permit, NOC, pollution, license, and fitness certificate
  • Track expiry dates, reminder schedules, and renewal status
  • Allow uploads and administrative review
  • Show upcoming renewal risks in dashboard and driver app

6.7 Multi-School Tenancy and URL Strategy

  • Each school should receive a dedicated dashboard URL such as schoolname.skippo.app or a mapped custom domain
  • The request host should determine the active school context before authentication and data access
  • All structured school data should live in PostgreSQL using a shared multi-tenant SQL model scoped by school_id or tenant_id
  • A central tenancy layer should store school metadata, subdomain settings, custom domains, feature flags, and branding configuration
  • Tenant-aware middleware and query patterns should ensure every request resolves the correct school context before any data access
  • The scale path should begin with one PostgreSQL deployment and evolve later through partitioning, read replicas, or tenant sharding if growth demands it

7. Technical Architecture

7.1 Backend

  • Framework: Django + Django REST Framework
  • Primary SQL datastore: PostgreSQL for all schools and all structured product data
  • Core backend pattern: Django-based multi-tenant platform with PostgreSQL as the source of truth and school-scoped data isolation
  • Tenant model: shared PostgreSQL database with tenant-aware tables, indexes, and service-layer scoping by school
  • Scaling path: start with shared PostgreSQL, then add partitioning, replicas, or selective sharding only when operational metrics justify it
  • Realtime and cache: Redis for Django Channels, caching, rate limiting, presence, and transient state
  • Tasks and queues: Celery + Redis for notifications, reminders, exports, and background jobs
  • Auth: JWT + OTP service integration
  • Storage: Cloudflare R2 or S3-compatible storage
  • Notifications: Firebase Admin SDK + SMS provider
Architecture note: PostgreSQL plus Redis is the recommended base for Skippo because it supports multi-tenant growth, concurrent writes, live tracking, reporting, and operational simplicity far better than per-school file databases.

7.2 Client Apps

  • Parent App: React Native with Expo, tuned for lightweight screens, aggressive caching, and efficient network usage
  • Driver App: React Native with Expo, built as a cross-platform app but optimized first for Android background location reliability
  • Teacher App: React Native with Expo or a mobile-first web app depending on rollout constraints
  • Dashboard: Next.js App Router with a premium design system
  • Efficiency strategy: use a shared-code monorepo with common UI primitives, auth flows, API clients, offline sync helpers, and notification logic across the parent and driver apps
  • Performance goal: reduce duplicate code, minimize bundle size, and keep API usage and battery consumption under control

7.3 Tenant Routing and Domain Model

  • Every incoming dashboard request should be resolved through subdomain or domain lookup
  • The tenant router should map the incoming school URL to the matching school record and tenant configuration in PostgreSQL
  • Dashboard branding, settings, feature flags, and messaging rules should load from tenant configuration
  • Platform super admins should be able to create schools, assign dashboard URLs, and manage tenant configuration centrally

10. Dashboard Design Direction

The school dashboard should not feel like a generic admin panel. It should be positioned as a premium operational cockpit for schools.

  • Use a bold visual identity and premium typography
  • Allow configurable widgets for transport, academics, compliance, and messaging
  • Support role-based dashboards for principal, transport admin, academic admin, and operations staff
  • Use live cards, maps, alerts, and actionable tables instead of flat CRUD-heavy layouts
  • Keep mobile and tablet responsiveness strong for school administrators in the field

11. Security and Permissions

  • Every record must be school-tenant scoped
  • Tenant resolution must happen before dashboard data access so one school can never read another school's data
  • Parents can only access their linked students
  • Teachers can only access assigned classes and students unless elevated by school policy
  • Drivers only access their assigned trip, vehicle, and compliance records
  • SOS and compliance actions should be fully auditable
  • Uploaded documents should use secure object storage and signed URLs

17. School Onboarding Playbook

This section describes the end-to-end operational process for bringing a new school onto the Skippo platform — from first contact through their first working day on the dashboard.

Step 1 — Interest Capture (School → Skippo)

A school administrator or decision-maker fills in the contact form on skippo.co.in. The backend creates a RegistrationInterest record with status pending. The Skippo operations team receives an automated email notification immediately.

Step 2 — Lead Review (Skippo Dashboard → Leads Module)

Any Skippo super-admin can open the Leads module at /dashboard/leads. The table shows all incoming enquiries with their status, school name, contact, and submission date. The team filters by status = pending to see new inbound interest. Leads progress through three statuses:

Status Meaning Who sets it
Pending Form submitted, not yet reviewed Auto-set on form submission
Contacted Team has spoken to the school; demo or follow-up scheduled Skippo ops team manually via PATCH on the lead
Onboarded School provisioned and credentials sent Auto-set when SchoolProvisionView is called with lead_id

Step 3 — School Provisioning (Skippo Super Admin)

Once the school agrees to onboard, a Skippo super-admin calls the School Provision API:

POST /api/tenancy/provision/

Body fields:
school_name — full display name (e.g. "Greenfield Public School")
school_slug — unique URL-safe ID (auto-derived if omitted, e.g. "greenfield-public")
admin_email — primary admin's email address
admin_name — admin's full name (optional)
lead_id — ID of the RegistrationInterest record (optional; auto-marks lead as Onboarded)

Response includes:
school.slug → this becomes the school's username / School ID
admin.username → same as admin email
admin.temp_password → a 12-character secure temporary password
school.dashboard_url → direct link to the school's dashboard login

The provisioning step automatically:

  • Creates a School record with a unique slug
  • Creates a TenantConfig (timezone, feature flags, logo URL placeholder)
  • Creates or updates the admin User account
  • Sets a temporary password on the admin account
  • Marks the linked lead as Onboarded

Step 4 — Credentials Delivery (Skippo → School Admin)

After provisioning, the Skippo ops team sends a Welcome Email to the admin containing:

  • School ID (username): their school_slug (e.g. greenfield-public)
  • Admin email (used as the login identifier)
  • Temporary password (from the provisioning API response)
  • Dashboard URL: https://dashboard.skippo.app/login?school=greenfield-public
  • Instructions to change the password on first login
Security note: The temporary password is single-use and should be changed by the admin on first login. It is returned only in the provisioning API response and transmitted only via the welcome email — it is never stored in plaintext on the server (Django's set_password hashes it with PBKDF2).

Step 5 — First Login (School Admin → Dashboard)

The school admin opens the dashboard login page and enters their School ID and admin email. The system sends a 6-digit OTP to the email; the admin enters it to complete authentication. On first login, the dashboard detects that TenantConfig.onboarding_complete = False and presents a First-Time Setup Banner.

Step 6 — First-Time Dashboard Setup

The settings page (/dashboard/settings) prompts the admin to complete their school profile. Key steps shown in the setup checklist:

Step Action Effect
1 Upload school logo (PNG / JPG / SVG, recommended 256×256 px) Logo stored in object storage; TenantConfig.logo_url updated; appears in sidebar and all school-branded surfaces
2 If no logo uploaded, school name initials are auto-generated as a placeholder avatar Two-letter initials (e.g. "GP" for Greenfield Public) shown with a navy gradient background everywhere a logo would appear
3 Confirm school name, timezone, and academic year Updates TenantConfig; affects all date-based reporting
4 Invite first teacher via the Teachers module Generates invite link; teacher receives signup email
5 Add first students and link parent phone numbers Parents can now log into the Parent App
6 Assign drivers and set up first route Driver App access unlocked; live tracking becomes operational

Once the admin saves the school profile, TenantConfig.onboarding_complete is set to True and the setup banner is dismissed permanently.

Logo Display Rules

  • If TenantConfig.logo_url is set → show the school's uploaded logo
  • If no logo uploaded → show a two-letter initial avatar (first letter of each word in the school name, max two letters) with a navy gradient background
  • The Skippo shield logo always appears separately as the platform brand mark — it is never replaced by the school logo
  • School logo appears in: dashboard sidebar school block, settings page, and any school-branded export headers

18. Final Recommendation

Skippo should be built as a modular school operations platform with transport as the initial wedge and parent trust as the retention engine. The strongest execution strategy is to build reliable core systems first, then layer the teacher experience, message center, compliance workflows, and premium dashboard experience on top.

For school onboarding, the combination of a clean provisioning API (school slug + admin email + temp password) and a first-time dashboard setup flow (logo upload, student import, teacher invite) creates a repeatable, low-friction path from sales close to first operational day.

If executed in this order, Skippo can launch a strong school pilot without losing the broader vision of becoming a full-stack operating system for school-parent coordination.
