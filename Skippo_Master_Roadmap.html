Skippo Master Product Blueprint and Roadmap

Version: 2.0
Date: April 13, 2026
Prepared For: Skippo product planning and engineering execution

1. Executive Summary

Skippo is no longer just a school transport safety platform. It should be positioned as a unified school operations platform that connects transport, classroom visibility, compliance, communications, and parent engagement.

The platform will support five primary surfaces:

  • Parent App: live transport tracking, alerts, student progress, attendance visibility, and message center.
  • Driver App: trip lifecycle, assigned vehicle, SOS, OTP login, and document renewal workflows.
  • Teacher App: classroom attendance, student progress updates, and parent-visible academic signals.
  • School Dashboard: highly flexible control center for transport, academics, staff, messaging, compliance, and reporting.
  • Backend Platform: APIs, auth, data models, real-time systems, notifications, analytics, and integrations.
Core product thesis: Schools need operational control, parents need trust and visibility, and staff need fast, low-friction tools. Skippo should become the operational layer connecting those needs.

2. Product Vision

Skippo should help schools answer five questions in real time:

  • Where is the student during the transport journey?
  • Was the student present in school and in class today?
  • Is the assigned driver, bus, and compliance documentation valid?
  • How can the school communicate updates and notices to parents reliably?
  • What operational risks require intervention right now?

6. Functional Requirements by Domain

6.1 Authentication and Sessions

  • OTP-based login for parents and drivers
  • School-managed login or OTP login for teachers
  • JWT-based API auth with refresh tokens
  • Device registration and device metadata tracking
  • Driver accounts may remain active on a maximum of two devices at a time
  • Session revocation from dashboard when needed

6.2 Transport Operations

  • Each driver is assigned exactly one active vehicle at a time
  • Each trip is linked to a route, driver, vehicle, school, and roster of students
  • Location updates broadcast every 10 seconds or every 20 meters
  • Trip events should be stored as an auditable timeline
  • Parents only see the trip relevant to their linked student

6.3 Academic Attendance and Progress

  • Teachers can mark daily attendance by class and section
  • Teachers can add short progress records linked to students
  • Parents can view student attendance and progress history
  • Dashboard can filter academic data by date, class, teacher, and student

6.4 Messaging and Ads

  • Message center stores all notices, updates, alerts, and ad-style campaigns
  • Messages can be targeted by school, class, route, or parent segment
  • Each message tracks publish time, delivery status, and read status
  • Ads should be clearly classified and controlled through dashboard permissions

6.5 Emergency Workflows

  • Driver SOS should instantly notify school admins and parents on the active route
  • The system should support configurable emergency escalation contacts per school or city
  • Civic-body automation should be designed as a configurable workflow and not hardcoded until verified integrations are available
  • Every SOS event should generate an audit trail

6.6 Compliance and Renewal

  • Store document types such as insurance, permit, NOC, pollution, license, and fitness certificate
  • Track expiry dates, reminder schedules, and renewal status
  • Allow uploads and administrative review
  • Show upcoming renewal risks in dashboard and driver app

6.7 Multi-School Tenancy and URL Strategy

  • Each school should receive a dedicated dashboard URL such as schoolname.skippo.app or a mapped custom domain
  • The request host should determine the active school context before authentication and data access
  • Each school should have its own isolated SQLite database in the initial architecture
  • A central registry layer should store school metadata, database mapping, subdomain settings, and domain configuration
  • Tenant-aware middleware and database routers should ensure every request resolves to the correct school database

7. Technical Architecture

7.1 Backend

  • Framework: Django + Django REST Framework
  • Core backend pattern: Django-based control plane with SQL persistence and tenant-aware routing
  • School data model: each school runs on its own isolated SQLite database in v1
  • Central registry: one SQL-backed registry database stores school records, domains, tenant routing metadata, and platform-level configuration
  • Realtime: Django Channels + Redis
  • Tasks: Celery + Redis
  • Auth: JWT + OTP service integration
  • Storage: Cloudflare R2 or S3-compatible storage
  • Notifications: Firebase Admin SDK + SMS provider
Architecture note: Per-school SQLite databases provide strong early isolation and simple portability for pilot schools, but they increase migration, backup, analytics, and cross-tenant reporting complexity. This approach is workable for v1 and should be re-evaluated before large-scale expansion.

7.2 Client Apps

  • Parent App: React Native with Expo, tuned for lightweight screens, aggressive caching, and efficient network usage
  • Driver App: React Native with Expo, built as a cross-platform app but optimized first for Android background location reliability
  • Teacher App: React Native with Expo or a mobile-first web app depending on rollout constraints
  • Dashboard: Next.js App Router with a premium design system
  • Efficiency strategy: use a shared-code monorepo with common UI primitives, auth flows, API clients, offline sync helpers, and notification logic across the parent and driver apps
  • Performance goal: reduce duplicate code, minimize bundle size, and keep API usage and battery consumption under control

7.3 Tenant Routing and Domain Model

  • Every incoming dashboard request should be resolved through subdomain or domain lookup
  • The tenant router should map the incoming school URL to its SQLite database and configuration
  • Dashboard branding, settings, feature flags, and messaging rules should load from tenant configuration
  • Platform super admins should be able to create schools, provision databases, and assign dashboard URLs centrally

10. Dashboard Design Direction

The school dashboard should not feel like a generic admin panel. It should be positioned as a premium operational cockpit for schools.

  • Use a bold visual identity and premium typography
  • Allow configurable widgets for transport, academics, compliance, and messaging
  • Support role-based dashboards for principal, transport admin, academic admin, and operations staff
  • Use live cards, maps, alerts, and actionable tables instead of flat CRUD-heavy layouts
  • Keep mobile and tablet responsiveness strong for school administrators in the field

11. Security and Permissions

  • Every record must be school-tenant scoped
  • Tenant resolution must happen before dashboard data access so one school can never read another school's database
  • Parents can only access their linked students
  • Teachers can only access assigned classes and students unless elevated by school policy
  • Drivers only access their assigned trip, vehicle, and compliance records
  • SOS and compliance actions should be fully auditable
  • Uploaded documents should use secure object storage and signed URLs

12. Development Roadmap

Phase 0: Discovery and Product Lock (1 week)

  • Validate pilot school requirements
  • Freeze MVP scope and field definitions
  • Create wireframes and system architecture
  • Decide rollout markets and emergency escalation policy

Phase 1: Backend Foundation (2 weeks)

  • Set up Django monolith or modular backend
  • Implement tenancy, roles, auth, OTP, device sessions
  • Set up central school registry, school-specific SQLite databases, and tenant database routers
  • Create core models and migrations
  • Set up admin panel, API docs, local development tooling

Phase 2: Transport Core (2 weeks)

  • Trips, routes, stops, vehicle assignment
  • Live location ingest and websocket streaming
  • Boarding and dropping flows
  • SOS event pipeline
  • Parent live tracking APIs

Phase 3: Driver App MVP (2 weeks)

  • OTP login and session handling
  • Assigned vehicle screen
  • Trip control and boarding list
  • Background location service
  • SOS UI and document reminders
  • Optimize shared code and network efficiency with the parent app architecture

Phase 4: Parent App MVP (2 weeks)

  • Login and linked student onboarding
  • Live trip screen
  • Alerts and trip history
  • Message center
  • Attendance and progress preview
  • Use shared cross-platform modules to maximize development and runtime efficiency

Phase 5: Teacher App MVP (2 weeks)

  • Teacher login
  • Attendance workflow
  • Progress note workflow
  • Parent-visible sync for attendance and progress

Phase 6: Dashboard MVP (3 weeks)

  • Premium UI system and dashboard shell
  • Live fleet module
  • Students, teachers, drivers, vehicles management
  • Messaging center
  • Compliance center
  • Reports and exports

Phase 7: Integrations and Pilot Hardening (2 weeks)

  • Push notifications and SMS fallback
  • Storage and media workflows
  • Monitoring, logging, and admin tooling
  • Field testing across real routes and real classrooms

Phase 8: Post-MVP Expansion (Ongoing)

  • Payments and subscriptions
  • DigiLocker and VAHAN integrations
  • Advanced academic insights
  • More automation in emergency response
  • School-specific branding and customization layers

15. Major Risks and Mitigations

Risk Impact Mitigation
Android background GPS reliability Critical Test early on multiple physical devices, use foreground services, tune update intervals
Emergency escalation expectations Critical Start with configurable contacts and documented workflows before claiming civic automation
Per-school SQLite operational overhead High Automate tenant provisioning, migrations, backups, and health checks from the central control plane
Too much scope in MVP High Ship reliable core workflows first and defer advanced integrations
Teacher adoption friction Medium Make attendance and progress entry fast with bulk actions and smart defaults
Dashboard complexity Medium Build a strong modular design system and a widget-based information architecture

16. Success Metrics for the Pilot

  • One pilot school live with transport and teacher attendance operational
  • 95 percent or better trip event delivery success
  • Parents actively use live tracking and message center weekly
  • Teacher attendance completion under 5 minutes per class
  • No critical issues in the happy path of trip start, board, drop, attendance sync, and parent notifications

17. Final Recommendation

Skippo should be built as a modular school operations platform with transport as the initial wedge and parent trust as the retention engine. The strongest execution strategy is to build reliable core systems first, then layer the teacher experience, message center, compliance workflows, and premium dashboard experience on top.

If executed in this order, Skippo can launch a strong school pilot without losing the broader vision of becoming a full-stack operating system for school-parent coordination.
